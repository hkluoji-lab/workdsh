# 示例、专业试用与成果

启动示例对应真实高频问题，包含必要输入和期望成果。示例只填充任务草稿，不自动发送，也不是已经完成的客户案例。

试用区分四种情形：有足够证据的典型任务；缺关键输入需要追问；材料矛盾需要指出；超出能力或权限需要说明边界。验收关注事实保真、方法是否实际使用、结论证据、未解决问题与交付完整性，不只看工具成功。

例：审核一份报价表，给出按约定口径的异常清单、理由和核验来源；价格来源缺失时不能编造市场价。例：将日报做成 PPT，需要分别检查事实、叙事与版式、编辑结果、实际 PPTX 下载，不能把大纲或创建记录当成最终制品。

明确草稿保存、结构校验、依赖锁定、用户 UI 发布、实际使用和文件交付是不同状态。没有运行真实模型就写“专业试用未执行”；没有文件就不写“附件已生成”。

遵守现有 validate→request_publish→受信 UI 预览确认流程。聊天确认不能替代 UI 发布操作。修改不会替换运行中任务；试用、召唤和切换只准备关联任务草稿。结果未知先复核，不重复制造副作用。

分析报告试用除了数值对账，还要逐项核对文字结论：单位假设是否被写成事实、子集是否被推广为总体、相关是否被写成因果、未知值是否在摘要中变成确定结论。数值JSON正确但报告文字越界仍不通过。单位未确认与部分数据缺失各保留一个反例，正常数据另保留一个基准案例。

交付声明应对应真实成果引用，并注明使用的专家修订、输入覆盖范围、已检查事项及未解决项。“发布成功”不代表专业案例通过；只验证过一个案例不能声称普遍可靠。缺文件、无法打开或必要内容缺失时说明实际状态，不以工具调用成功代替最终成果。
