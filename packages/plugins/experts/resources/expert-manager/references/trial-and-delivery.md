# 示例、专业试用与成果

启动示例对应真实高频问题，包含必要输入和期望成果。示例只填充任务草稿，不自动发送，也不是已经完成的客户案例。

按职责选择代表性正常任务，再根据风险选择必要的异常试用，不机械要求每次创建执行全部案例。可考虑四种情形：有足够证据的典型任务；缺关键输入需要追问；材料矛盾需要指出；超出能力或权限需要说明边界。验收关注事实保真、方法是否实际使用、结论证据、未解决问题与交付完整性，不只看工具成功。

例：审核一份报价表，给出按约定口径的异常清单、理由和核验来源；价格来源缺失时不能编造市场价。例：将日报做成 PPT，需要分别检查事实、叙事与版式、编辑结果、实际 PPTX 下载，不能把大纲或创建记录当成最终制品。

明确草稿保存、结构校验、依赖锁定、用户 UI 发布、实际使用和文件交付是不同状态。没有运行真实模型就写“专业试用未执行”；没有文件就不写“附件已生成”。

遵守现有 validate→request_publish→受信 UI 预览确认流程。聊天确认不能替代 UI 发布操作。修改不会替换运行中任务；试用、召唤和切换只准备关联任务草稿。结果未知先复核，不重复制造副作用。

检查成果时以创建时约定的标准为准。写作检查事实、受众、风格及来源；研究检查引用是否支持结论和不确定性；代码检查实际行为与运行证据；设计检查真实呈现、适用尺寸及输出文件；分析同时核对计算口径、数值和文字结论。按任务选择相关项目，不能用 JSON 合法、工具成功或截图存在替代专业成果检查。

成果交付前抽查每条新增事实与承诺能否指向材料。特别检查来源元数据（作者、机构、内外部属性、独立性、审批/验证）和未来行动（推出、通知、价格、时间）：缺证据就删去或标为未知，不用标题、引用编号或专业语气补证据。事实、带条件推断与建议分开。检查应覆盖正文、标题、摘要和表格；短成果不必公开冗长核对台账，但不能略过事实核对。

试用失败先保留输入、实际成果与可复现问题，区分：定义中的步骤或边界不清、所需能力不可用、执行没有遵守已有方法。前两类可提出通用方法或能力配置改进；执行错误不能直接证明需要新增 Skill。建议修改应能适用于同类新任务，不能把该次答案硬编码进定义。更新仍走同一草稿、revision 校验和受信 UI 发布流程；用有变化的代表性案例检查改进，未运行就明确标注。不要自动重新发送任务或无限重试。

以上是制作与评审指导，不是已经实现的自动专业评分或发布拦截。用户决定是否试用；发布成功、结构校验通过和专业试用通过分别报告。

交付声明应对应真实成果引用，并注明使用的专家修订、输入覆盖范围、已检查事项及未解决项。“发布成功”不代表专业案例通过；只验证过一个案例不能声称普遍可靠。缺文件、无法打开或必要内容缺失时说明实际状态，不以工具调用成功代替最终成果。
